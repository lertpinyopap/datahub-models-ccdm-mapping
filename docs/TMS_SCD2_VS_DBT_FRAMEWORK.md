| Audit/job hooks | Runs | Runs | Usually not present unless added manually |
| Generated SQL size | Larger | Smaller than true, but still larger than native dbt | Generally leaner |

The practical flows are:

```text
TMS, validation_enabled: true

__source
  -> source validation / quarantine guard
  -> typed rows
  -> SCD2 change detection
  -> duplicate and boundary handling
  -> affected-key reconstruction
  -> SCD2 validation
  -> incremental delete+insert
  -> target
```

```text
TMS, validation_enabled: false

__source
  -> typed rows
  -> SCD2 change detection
  -> duplicate and boundary handling
  -> affected-key reconstruction
  -> SCD2 validation still runs
  -> incremental delete+insert
  -> target
```

```text
Pure dbt, native_scd2_validation: false

staging/source SQL
  -> typed source rows
  -> SCD2 change detection
  -> affected-key reconstruction
  -> incremental delete+insert
  -> target
```

```text
Pure dbt, native_scd2_validation: true

staging/source SQL
  -> typed source rows
  -> SCD2 change detection
  -> affected-key reconstruction
  -> native SCD2 validation
  -> incremental delete+insert
  -> target
```

The important difference is that TMS `validation_enabled: false` currently disables general source validation, not all SCD2 validation. Pure dbt’s `native_scd2_validation: false` disables its optional SCD2 validation CTE entirely.

| Task | Why TMS runs it | What it does | Typical cost |
|---|---|---|---|
| Duplicate-hash boundary handling | Protects SCD2 history from redundant or duplicate versions | If an incoming row has the same business-data hash as an adjacent historical version, it adjusts the surrounding `VALID_TO_DATETIME` boundaries instead of creating unnecessary duplicate history | Usually small to moderate. Can increase when many affected keys or large target history must be read |
| SCD2 validity validation | Prevents invalid SCD2 windows from being loaded | Checks for null dates, `VALID_TO <= VALID_FROM`, overlaps, and, for `continuous`, gaps or missing end-of-time rows | Potentially the most expensive. `affected_window` is usually moderate; `full_target` can be expensive because it scans all target history |
| Diagnostic duplicate-hash query | Provides operational visibility into skipped/updated duplicate hashes | Counts rows that match existing hashes and logs metrics such as `current duplicate rows skipped` | Usually small to moderate, but it can be expensive if it scans a large target. It does not change data |

Pure dbt makes these optional because a lean framework may prefer:

```text
less SQL
fewer target scans
faster execution
```

while TMS prioritises:

```text
stronger correctness checks
standardised SCD2 behaviour
operational diagnostics
```

The important distinction is:

- Duplicate-hash boundary handling is part of the actual SCD2 transformation and can affect loaded history.
- SCD2 validity validation is a correctness guard and can fail the load.
- Diagnostic duplicate-hash logging only reports counts and does not affect the result.

For performance, the usual priority is:

1. `full_target` SCD2 validation: highest possible cost.
2. Duplicate-boundary handling over a large target: potentially moderate/high.
3. `affected_window` validation: usually lower.
4. Diagnostic logging: often small, but still unnecessary overhead if you do not need the metrics.

In your case, the `205930` count means many incoming rows matched existing current hashes. The number itself does not prove that the diagnostic query was expensive; Snowflake query history/profile is needed to measure its exact runtime.
